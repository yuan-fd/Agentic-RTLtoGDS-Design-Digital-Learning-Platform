审计口径：本章是基于当前工作树、公开入口和 16 份选定验收摘要的聚焦审计，不是逐行安全审计或工业资格认证。技术发现先讲问题与证据，再讲改进；未重跑 EDA，不把旧文档测试数当作本轮测试。

1. 锐评：你的地基比自我总结强，产品承诺比证据大

这是一个已经具备真实执行和审计基础的研究集成平台，但还不是能读公司规格书、自主诊断并跨层闭合设计的通用工作台。最危险的不是“小 case 太小”，而是不同协议、不同版本、不同成熟度的能力在叙述中被串成了一个已完成产品。

你在 Word 中担心“只是 JSON + baseline”，这个担忧指出了智能性问题，但低估了后续代码里的原生插件反馈、可信产物和恢复控制。相反，把“已经有四域诊断”“能恢复 RTL”“已接入 benchmark”直接说成“能定位根因、自动修复、达到 benchmark 准确率”，又会高估现状。[[E01]][[E02]][[E03]][[E05]][[E11]]

2. 优先级最高的五个问题

P0 · A2 当前协议与固定用户目标存在语义差距

证据：评价代码以候选 CLK 作为对应时钟输入，元数据标注 candidate-variable-clock-signoff 和 fixed_sdc_fair_comparison=false；handoff 构建完整上游域及预算。[[C14]][[C15]]

影响：不能把“面积至多增加 3%、不改 SDC、最多 3 次”的 L1 请求，无条件解释成同一目标下的 151 次 A2 可变时钟优化。代码有授权记录，并不自动证明所有用户约束已经作了等价映射。

建议：先明确分成两种实验语义：固定用户目标的工作台任务、完整上游研究协议的 A2 campaign；跨越时展示差异并重新授权。固定目标模式是否能由上游原生支持，须先验证；不得为了兼容而静默冻结搜索维度、改评价器或宣称精确复现。

P1 · Tutorial 的源码 hands-on 仍没有真实闭环验收

证据：当前治理总览只审 L1/L2；产品角色允许列表列出 RTLScout、A2、ORAssistant 与独立 3D，不能从中推出已完成 L3/L4 教程能力。[[C05]]

影响：如果今天把“已有插件架构”汇报为“proposal 已实现”，专业听众会追问 patch、构建和完整评价证据，而现有 L1/L2 smoke 无法回答。

建议：一个上游、一个机制、一份明确改动白名单、一个受保护设计和预算；先完成原生源码候选闭环，再谈平台接入。失败候选也能教学，但不能没有真实执行。

P1 · 诊断名称与算法能力需要分层说明

证据：_headroom() 是阈值余量；diagnose_runtime() 主要做事实归一化、保守假设和下一步检查建议。控制状态验收是 role/state replay；当前跨阶段实验恢复已知干净版本，而非自动生成新修复。[[C12]][[C13]][[E06]][[E03]]

影响：“diagnosis-agent”“repair-agent”“PDAgent-style”这些名字容易让人误以为实现了上游完整算法。结构启发、数据接口、原生算法复用、准确率验证必须分别标注。

建议：界面分开显示事实、未知项、规则提示、模型假设、验证过的结论；补充任务集测试，而不是增加描述性组件。

P1 · 有多个能力入口，但还不是一条一致的用户旅程

证据：治理验收文档明确指出 SpecIR、RTLScout、诊断/恢复和 A2 还没有全部整合成一个完整用户界面。工作台服务与旧网页并存；旧页面仍包含“唯一 BO/GP 优化入口”文字，与当前 A2 产品口径冲突。该结论来自静态源码，未做浏览器操作验证。[[C16]][[C24]][[E10]]

建议：先做同一 Goal、候选谱系、Runtime 和协议的只读整合与导航，不在 UI 重算权威状态；之后再加最小提交动作。不要一次重构 API、UI、Runtime 和优化器。

P2 · 贡献文档与变更切片存在维护债务

证据：现有 CONTRIBUTING 的中文尾段称“缺少顶层 LICENSE”，但根目录已存在 MIT LICENSE。[[C17]][[C18]] 另有 4 份被选摘要的治理文档没有内嵌摘要哈希，本轮只补充记录在报告中；这不是哈希不一致，但不利于独立评审。

开始本轮时存在 193 条工作树状态记录，跨代码、集成、脚本与文档；apps/api/app.py 为 5,277 行。文件大或工作树脏本身不证明设计错误，但会增加新贡献者定位、切片审查和精确回滚的成本。不要用“清理”名义删除历史；先按治理清单分类。

4. 按单一切片推进：每一步都给验收产物

建议路线，不是工期承诺今天只交报告，不启动长程实验或修改受保护组件。以下优先级按依赖和风险排序，不把“预计几天”伪装成已经验证的开发周期。

切片唯一边界 / 预计文件范围验收与停止条件
S0 口径与协议决策治理文档与实验描述；不改运行逻辑。列明固定目标与 A2 可变时钟的差异、允许变化、预算与授权。不能核实兼容性则停，不修改裁判。
S1 同一任务的证据旅程一个工作台只读展示切片：页面/视图与已有查询服务的组合。可从 Goal 找到候选、验证、run、诊断与 campaign；全部值来自权威存储，刷新不重跑。缺接口则拆下一切片，不顺手改 Runtime。
S2 L1 行为评测测试任务与评测脚本；固定工具集合和预算。覆盖澄清、只读比较、越权拒绝、未知诊断、恢复等情况。先给覆盖率和失败例，不追求漂亮总分。
S3 A2 正式 campaign单独实验协议、批准资源、既有 worker 执行；不同时改搜索策略。151 次配置对应的完整终态、失败、成本和重启记录；若比较优势，额外冻结公平对照与统计。模型/工具版本变化则重新命名实验。
S4 经典模块 spec 契约选择一个含状态模块，完成需求/验证任务定义。规格摄取、逐项确认和冻结验证；缺独立 oracle 则不能宣称公司级 spec 支持。不改 RTLScout 内核。
S5 L3 原生准入一个候选上游 intake + 原生 smoke；随后另一个 adapter 切片。准确版本、许可、checkpoint 前置条件、动作白名单、失败证据。需要重写上游算法则停。
S6 L4 原生机制实验一个受限源码域的原生构建/评价协议；平台适配另切片。patch、二进制哈希、构建和完整评价；评价器/benchmark 必须改才能得分则停。
S7 跨能力规划待 L2/L3/L4 各自可用后，单独接入或研究合法动作选择策略。同工具、同预算对比固定流程；检查反馈敏感性与失败恢复，不以模型自述判断智能。

5. 正式停止记录：固定目标与上游协议不等价

Problem：固定 SDC、严格小预算的用户任务，与当前完整 A2 可变时钟实验不是等价协议。

Evidence：fixed_sdc_fair_comparison=false；完整 12 维搜索域；151 次预算配置。[[C14]][[C15]][[E10]]

Why the current plan fails：若仅把“L2 插件已接入”视作所有 L1 目标的透明延续，会使用户约束和实验比较口径发生变化。

Option A：保留上游原生研究协议为独立明确授权的 campaign；固定用户目标任务保持原边界，缺优化能力时直接说明。

Option B：先核实上游是否原生支持所需固定目标；可支持则单独审查适配与验收，不可支持则寻找其他获准能力或与上游合作。

Recommendation：今天采用 A 的汇报口径，同时把 B 列为前置研究任务。不修改评价器，不悄悄裁剪维度，不把两类结果合成一条公平比较曲线。

6. 给你个人的建设建议

  • 不要一个人扮演所有算法作者。你要能解释输入、输出、状态、评价和研究边界；上游作者负责算法内核，这是平台路线的优势。
  • 每次只追一个闭环缺口。例如“同一 run 的失败证据能否驱动可审计恢复”，而不是一次要求“更智能、更漂亮、更通用”。
  • 用证据区分工程成果和科研贡献。原生接入、权限、恢复与公平协议是有价值的工程成果；通用规划、更优 QoR 或诊断算法是需要对照实验的研究主张。
  • 少报功能数，多报可复查任务。一个失败被正确识别、恢复并保留证据的案例，比十个没有验收的 agent 名字更有说服力。
