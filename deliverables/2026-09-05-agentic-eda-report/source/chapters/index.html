三个必须当场说明的边界

① L1 不是 baseline 启动器

L1 是用户理解、澄清、观察、决策解释和授权的交互入口。RTL 生成/验证和基础实现是平台的基础能力；L2/L3/L4 是可调度的优化能力，而不是平台全部模块。

② 固定时钟与可变时钟不是同一个实验

当前 A2 走完整 12 维可变时钟域，评价元数据明确写着 fixed_sdc_fair_comparison=false。不能直接承诺它延续了“SDC 不变、最多 3 次”的用户任务。[[C14]][[C15]]

③ 完整 tutorial 的最大缺口不是再多一个 dashboard。proposal 的第 5 节明确要求受限源码修改、重编译、评价与保留/拒绝。L1/L2 的有界闭环是必要基础，但不能替代第二个 hands-on。把源码部分标成待建设，比临时用伪代码演示冒充完成更可信。

今天向老师建议作出的决定

  1. 确认双层范围：完整平台面向教学级 Spec-to-GDS；教程主要深入“自然语言工具闭环”和“目标驱动源码演化”两条链。
  2. 近期先做证据闭环，不扩菜单：以同一设计、同一目标呈现状态、行动、反馈与拒绝原因；明确 A2 协议切换的授权差异。
  3. 长 campaign 单独审批：先确认资源、版本、协议和比较对象，再启动 151 次测量；今天不为汇报临时启动。
  4. L3/L4 先定一个原生上游与一个受限目标：完成许可、版本、原生 smoke 和适配边界，不让平台开发者重写研究算法。

这份报告怎样读？

  1. Tutorial 解读原文到底承诺什么；L1—L4 怎么对应。
  2. 功能、代码与 Workflow确认 spec 后先做什么；每个模块的输入、输出和权限。
  3. 算法原理与智能工作台从反馈闭环到 BO、局部动作与源码演化，有限工具如何组合。
  4. 现状锐评和后续行动有证据的强项、真实缺口、单一迁移切片。
  5. 可交给同学的贡献者指南接插件流程、最小协议示例、分工与 PR 验收清单。
  6. 直接用于汇报和 Workshop讲稿、三小时议程、演示证据、练习和答疑。
  7. 证据、文献与术语复核方法、路径、哈希、代码行和原始来源。
