本章的中心问题：智能工作台不是把“分析、规划、反思”几个词显示出来，而是能够依据新证据改变计划，并让这个改变可以被检查。专业搜索、修复和源码演化算法优先复用上游；平台不能以几条规则冒充这些算法。

1. 先把“智能”拆成可实现、可评价的五种能力

能力最小可检查行为常见假象
目标理解把意图、硬约束、偏好与未知项分开；语义等价的说法保持同一限制。抽几个关键词形成 JSON，就说理解了复杂规格。
设计观察读取有版本、有 run/阶段来源的证据；缺失值明确 unknown。把未解析的 DRC 填成 0，把预测当实测。
诊断给出有依据、能被进一步证据推翻的假设。看到 WNS 差和拥塞高，就宣称拥塞一定是根因。
行动选择在合法能力中选择查询、实验、优化、恢复或停止，解释条件和成本。不管反馈如何，总是执行预写好的下一步。
经验复用携带设计/工艺/工具范围、失败与反证、来源和使用门槛。保存一段“某参数效果很好”，就说学会了。

抽取结构化事实本身不是低价值工作。专业算法必须依赖可信数据。问题是不能把“观测层已完成”表述成“推理、因果诊断和策略选择都已完成”。

2. 一次可信的诊断，不是从指标直接跳到修复

观察记录哪里未满足与证据来源
→
假设提出可被推翻的机制解释
→
检查补信息或做受控干预
→
更新保留、降低置信或更换假设

解释性示例若布线后 timing 退化，不能只依据一份全局拥塞指标决定降低密度。应核对关键路径、阶段差异、局部拥塞和延迟构成；必要时，在同一协议与预算内做能区分假设的对照。一个同时改了许多参数的优化候选，即使更好，也不自动证明其中某个参数是因果原因。

当前 diagnose_runtime() 会在 timing 与拥塞均违约时生成保守关联假设，并建议进一步核对路径位置；全局拥塞不支持该解释时会保留反证。这个设计诚实且有用，但仍是规则化的证据提示，不是广泛验证过的根因定位算法。[[C13]][[E05]]

“还差多少”与“还能优化多少”必须分开

目标差距 / 约束余量

面积上限 103、当前 100，余量是 3；时序目标尚未满足，可以计算与阈值的距离。这是测量与阈值的算术关系。

上界约束：margin = limit - measured
下界约束：margin = measured - limit

当前 _headroom() 正是这种阈值余量计算。[[C12]]

可实现优化潜力

“在不违反功能和面积要求的情况下，还能改善多少 timing”需要探索证据、模型及误差范围。不能从单个 margin 直接得出。

第一版可以诚实地说“潜力未知，下一步实验旨在降低不确定性”，不必输出虚假的百分比。

3. L2 参数搜索：为什么不是让模型随便改几个数字？

把一次物理实现记作 y = F(x; D, P, s)。x 是授权参数，D 是设计，P 是协议和工具环境，s 是种子，y 包含指标、合格性和失败。Runtime 求一次 F；优化器选择下一组 x。这是两种职责。

H_t = {(x_i, 实测结果_i, 合格性_i, 失败_i, 证据_i)}
x_(t+1) = 上游策略(H_t, 目标, 搜索域, 剩余预算)
新结果 = Runtime 执行并经受保护评价
H_(t+1) = H_t 加入新结果

用 BO 解释“探索”与“利用”（教学原理，不是新建本地算法）

昂贵黑盒优化通常不适合把所有参数组合跑完。代理模型根据历史样本估计某组参数的结果与不确定性；采集策略在“预计更好”与“值得进一步了解”之间权衡。以下 Expected Improvement 只是帮助理解的通用最小化例子，不是对 A2 当前每轮策略的完整复刻：

EI(x) = E[max(0, f_best - f(x)) | H_t]

这个式子的意思是：在已有数据条件下，尝试 x 的预期改善有多大。涉及多个目标、失败和硬约束时，还要遵守明确的目标与可行性定义；不能用一个临时加权分数替换受保护评价。

当前锁定 A2 的原生路径包含 inspection、建模、GPR 反馈、配置与候选选择；平台 adapter 调用它的原生 workflow，并保存检索、模型调用、候选与上下文。应讲上游如何做研究决策，而不是在平台再写一套廉价 BO。提供模型替换和参数域绑定时必须披露其与论文环境的差异。[[C11]][[R04]]

当前实证最值得展示的是“不合格也进入反馈”

A2 单反馈验收中，真实候选执行状态为 succeeded，但反馈 feasible=false；然后原生策略产生下一组候选。三个结论要分开：程序运行完成、工程要求达标、优化优于比较对象。此次只支持有界反馈集成，不支持后两项普遍结论。[[E02]]

4. L3 有限动作：动作有限，策略仍然可以很复杂

将状态记为 s_t，可用动作集合记为 A(s_t)。一个动作不是只有名字，还包含对象、参数和前置条件。动作产生候选状态，再经检查形成新观测。算法难点在于对哪里、何时、以什么顺序和参数做动作，而非无限增加命令。

合格 checkpoint
  → 诊断 / 原生策略选择获准动作
  → Runtime 在候选工作区执行变换
  → 必需的功能、物理和 QoR 检查
  → 接受、拒绝或继续；保留父版本与失败产物

OpenROAD 的 repair_timing 和 repair_design 已有原生实现，平台不需要重写相应引擎。把它们作为 L3 能力时，还要定义状态装载、允许写集、分析前置条件、验证与回退，而不只是包一层字符串调用。[[R10]]

可复用研究候选：ResizerAgent 的作者项目围绕 post-CTS 设计，根据 timing/物理反馈和历史选择修复计划与相关操作，适合作为“有限动作也能做研究闭环”的例子。它的环境、入口、许可、工具版本与平台 smoke 尚需单独 intake；本报告不宣称你们已接入。[[R05]]

5. L4 源码演化：不是让模型在 OpenROAD 仓库随便改

冻结实验协议与基线工具
  → 从最终未满足目标形成机制假设
  → 选定允许修改的源码范围
  → 上游演化插件产生 patch
  → 路径 / 权限检查
  → 独立构建、测试与原生检查
  → Runtime 执行固定设计流程
  → 受保护评价，保留全部候选与失败
  → 根据证据保留 / 拒绝 / 修订假设

源码改变后，候选工具二进制当然会改变。公平性不是要求“二进制完全不变”，而是把允许变化的引擎实现作为实验处理，将其他评价条件固定。需要绑定基线 commit、patch 哈希、构建配方、候选二进制、固定设计和评价版本，避免链接到缓存旧二进制或修改裁判。

GoalEvolve 的 2026 年 8 月预印本研究如何由最终目标差距定位主要瓶颈，再结合阶段证据缩小到机制与源码区域，并记录局部收益在下游的保留或退化。它比“源码随机搜索”更贴近 proposal 后半段。论文效果不等于本平台效果；本轮没有完成其可执行代码、许可和原生入口准入。[[R06]]

为什么局部收益不够？例如某个阶段的 timing 变好，后续可能产生面积、功耗或布线代价。仅展示阶段最优日志，会把下游问题隐藏掉。源码候选是否有价值，必须回到事先冻结的完整评价条件；单次改善也不能证明跨设计泛化。

6. 外层如何决定先查询、继续 L2，还是申请 L3/L4？

建议架构，非已验证通用规划器分两步做：第一步由确定性控制逻辑筛掉不合法动作；第二步由获准的研究策略在合法集合中选择。不要让 LLM 自行决定自己是否有权限。

A_legal = 注册能力 ∩ 当前状态可用 ∩ 用户允许 ∩ 环境可用 ∩ 预算可承受
下一行动 = 策略(目标, 证据, 未知项, 历史, A_legal)
观察到的情况建议行动方向不能直接推断
缺关键路径或阶段数据先查询或补充分析；说明成本与想排除的假设。没有数据，所以修改所有相关参数。
有合法搜索域，预算获准调用 L2，保留其内部原生策略。所有用户的固定约束都与现有 A2 域相容。
适用 checkpoint + 已准入局部能力根据诊断证据考虑 L3；满足前置验证。一次不改善就说明必须修改引擎。
证据支持机制限制，且允许源码实验申请明确范围的 L4 独立实验。源码修改必然比参数搜索强。
预算用尽、目标已达成或风险过高停止、交付现有最优可行结果与未解决项。为了展示“反思”而继续跑。

停滞判断只是控制信号，不是算法最优证明

当前 convergence 分类会检查同协议的有效尾序列：最新失败或成功点不足则 unknown；方向归一化后，以绝对/相对容差判断改善、连续退化或窗口停滞。它不丢掉失败再拼出“好看的曲线”。stalled 不等于全局收敛，更不等于已证明需要 L4。[[C20]][[E08]]

7. 有限 tool registry 怎样面对无限问法？

不要为“UART timing 差”“FIFO timing 差”分别注册工具。应注册带对象、阶段和参数的查询/执行能力，让规划器组合它们。用户说“面积下降但时序变差，为什么”，可转换成识别版本、检查可比性、比较指标、定位阶段和请求进一步诊断的序列。

情况系统应做什么
工具已有，只是表述不同语义理解、补参数、组合已有能力。用表述变化测试约束保持。
工具已有，但缺证据/状态查询、准备获准 checkpoint，或追问；不得伪造输入。
外部项目可能支持，尚未准入记录能力缺口，走贡献者 intake；正常会话不负责临时安装。
当前完全不支持说清不能完成的部分、可完成的子任务和人工接手点。

“灵活”来自类型化工具的参数化、组合、条件分支和反馈，不来自开放任意 shell。允许扩展插件，不等于允许运行中的 agent 自行扩大权限。

8. 工作台应该展示什么，才不是大模型自言自语？

建议的决策卡 · 非当前 UI 截图教学假设数据
目标
改善 setup timing，保持本轮 RTL 与验收约束不变。
事实
阶段报告显示布线后退化；引用对应 run、阶段、报告和哈希。没有相应证据的值显示 unavailable。
假设
局部布线变化可能影响关键路径。状态：待验证，非已确定根因。
候选动作
补充路径查询；请求参数搜索；请求局部修复。只展示通过前置筛选的能力。
本次选择
先补信息，因为当前证据不足以区分两种解释。
如何验证
结果支持假设则进入相应实验；结果不支持则降低假设优先级；无证据则请求人工判断。
执行回执
实际 Policy 决定、Runtime task/run ID、状态、预算消耗和新产物必须跟在卡片之后。

展示的是可核对的行动依据与结果，不是内部隐藏思维链。模型可以解释理由，但不能用一段事后合理化文字代替真实工具轨迹。长期目标是“解释与执行一致”，不是“模型说得像专家”。

10. 怎样证明工作台真的比固定脚本强？

建议评价协议围绕小而明确的任务集冻结支持范围与预算，对比相同工具集合下的固定流程、基础工具 agent 和增强策略。不要给增强策略更多预算、隐藏标签或额外工具，再把优势归因于“智能”。

  • 目标保持：不同表述是否保持同样的硬约束、未知项和授权范围。
  • 行动合法：是否正确拒绝缺 checkpoint、超预算、越权或不支持的操作。
  • 证据响应：反馈或反证变化时，动作是否发生合理变化；可以允许多个正确行动。
  • 诊断质量：是否命中任务允许的假设/检查范围，是否给出可定位证据，而非仅评价文笔。
  • 最终价值：成功率、可行结果、最终 QoR、达到目标所用预算、失败和恢复率；预测单列。
  • 可复现性：多设计、多种子与独立复跑；保留失败，不只报最好一个。
实际建设顺序：先让一个边界明确的任务做到“有证据地选择/拒绝行动”，再扩任务集和研究策略。不要把“准确预测所有设计的最佳工具”作为第一版上线条件。
