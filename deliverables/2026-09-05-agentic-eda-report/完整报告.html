从会用工具，到能改进工具

3. L1—L4 是能力分类，不是顺序流水线

用户分类建议定义在 proposal 中的位置
L1面向人的目标澄清、查询、行动解释、授权和反馈交互。算法不必放在 UI 内。1—3 的主干，并贯穿后续实验。

4. 全平台 Spec-to-GDS 为什么仍然成立？

建议范围平台可以提供 spec、RTL、已有实现 checkpoint 三类入口。它们经过不同的前置检查，最终汇入共同的执行与评价基础设施。教程从已验证 RTL 开始，是降低教学变量的选择，不是产品架构的能力上限。

平台愿景

经典模块的受控改造：规格澄清 → 前端生成/复用 → 验证 → 后端实现 → 优化 → 教学级交付。需要说明支持的模块族、接口、工艺和验证条件。

教程聚焦

三小时不可能讲透所有前端、验证和物理设计算法。前端可作为入口演示；专业深度集中在工具闭环、可信评价、参数搜索与源码演化。

5. 怎样判断“完成 tutorial”，而不是只完成了演示网页？

  1. 能够复现交互：同一问题的不同说法不会偷偷改变约束；未知信息会被追问或标记。
  2. 能够验证执行：参与者能看到真实 run、attempt、产物和终态，而非只有模型描述。
  3. 能够观察反馈影响：至少展示一次根据新证据继续、停止、拒绝、修订或恢复。
  4. 能够完成源码闭环：至少一个锁定原生项目的受限源码候选完成构建与评价；成功或失败均可成为教学材料，但必须有完整链。
  5. 能够解释评价边界：为什么某次流程成功却不合格；为什么局部收益不是最终收益；为什么 smoke 不是统计优势。

我们搭建的不是一个本地自研优化器合集，而是一个外部研究能力可以可靠协作的平台。用户先确认设计目标，专业插件提出设计或优化候选，Runtime 负责真实执行，受保护评价器判断结果。教程先展示自然语言如何触发可靠工具闭环，再展示如何在固定评价条件下改进 OpenROAD 的内部算法。目前前一条链已有有界证据，后一条链仍是明确的后续建设目标。

2. 从一个 UART 改造规格开始：第一次工作不是优化

教学设计示例，未验收用户希望在经典 UART 上增加 APB 接口、深度 16 的接收 FIFO、可配置波特率和错误状态，使用指定开源工艺完成教学级版图。这个示例用于解释职责，不能拿当前 8 位加法器验收替它背书。

① 需求澄清：先把“对”定义出来

输入：规格书、自然语言、可复用项目版本。工作：澄清 FIFO 满/空行为、复位、寄存器语义、配置生效时机、接口时序、时钟和验收目标。输出：用户确认的 SpecIR、需求编号、验证计划、DesignGoal、权限和预算。

系统不能把“低功耗”偷偷解释为任意数值。默认值要标成建议，经确认后再冻结。对于上传文件，本次未验证已具备通用 PDF/DOCX 规格摄取能力。

② 执行前检查：决定任务是否具备条件

检查可复用源码权限、接口和工艺支持、验证入口、工具环境、输入哈希、资源预算。输出可执行计划或具体阻塞项。此时不需要 L2，也不应该盲目生成 RTL。

③ 前端设计插件：产生第一个候选

调用获准 RTL 生成/复用能力，保存候选与来源。验证组件依据冻结需求检查候选，把编译、仿真、反例等反馈给原生设计插件。这里已经有“候选 → 检查 → 修订”的闭环。当前原生 RTLScout 的单任务例子有真实证据。E01C26

④ 前端验收：形成精确 checkpoint

区分语法可编译、功能通过当前检查、测试质量三个结论。同一模型生成 RTL 和 testbench 互相认可，并不足以证明需求正确。保存需求版本、冻结 oracle、验证覆盖、候选哈希与未覆盖项。

当前加法器的穷举对这个组合逻辑任务很有说服力，但不能外推到包含复杂状态的设计。mutation gate 说明测试能捕获所选扰动，也不等于任意缺陷都可检测。

⑤ 基础实现：建立第一份物理证据

Runtime 提交受控综合/布局/CTS/布线任务，采集阶段报告与最终结果。baseline 是比较基准，也是把“这个设计在此条件下怎么样”变成事实的第一步；它不是 L1 的全部价值。

⑥ 观察与优化：此时才挑选 L2/L3/L4

目标已满足则交付；信息不足则补充查询；适合参数搜索则请求 L2；具备受控 checkpoint 和局部修复能力才考虑 L3；证据和授权支持机制实验才考虑 L4。没有适用能力时必须停止或请求人工，而不是让模型自行执行 shell。

⑦ 交付：给结果，也给剩余风险

交付规格版本、RTL、验证结果、GDS、约束、工具版本、QoR、失败历史和未满足项。应明确“教学级”，不以文件存在代替功能或签核结论。

算法机制与智能工作台

让证据改变下一步行动

理解参数优化、有限动作、源码演化与诊断；知道“智能”来自哪里，又该如何验证。

本章的中心问题：智能工作台不是把“分析、规划、反思”几个词显示出来，而是能够依据新证据改变计划，并让这个改变可以被检查。专业搜索、修复和源码演化算法优先复用上游；平台不能以几条规则冒充这些算法。

1. 先把“智能”拆成可实现、可评价的五种能力

能力最小可检查行为常见假象
目标理解把意图、硬约束、偏好与未知项分开；语义等价的说法保持同一限制。抽几个关键词形成 JSON，就说理解了复杂规格。
设计观察读取有版本、有 run/阶段来源的证据；缺失值明确 unknown。把未解析的 DRC 填成 0，把预测当实测。
诊断给出有依据、能被进一步证据推翻的假设。看到 WNS 差和拥塞高，就宣称拥塞一定是根因。
行动选择在合法能力中选择查询、实验、优化、恢复或停止，解释条件和成本。不管反馈如何，总是执行预写好的下一步。
经验复用携带设计/工艺/工具范围、失败与反证、来源和使用门槛。保存一段“某参数效果很好”，就说学会了。

抽取结构化事实本身不是低价值工作。专业算法必须依赖可信数据。问题是不能把“观测层已完成”表述成“推理、因果诊断和策略选择都已完成”。

2. 一次可信的诊断，不是从指标直接跳到修复

观察记录哪里未满足与证据来源
→
假设提出可被推翻的机制解释
→
检查补信息或做受控干预
→
更新保留、降低置信或更换假设

解释性示例若布线后 timing 退化，不能只依据一份全局拥塞指标决定降低密度。应核对关键路径、阶段差异、局部拥塞和延迟构成；必要时，在同一协议与预算内做能区分假设的对照。一个同时改了许多参数的优化候选，即使更好，也不自动证明其中某个参数是因果原因。

当前 diagnose_runtime() 会在 timing 与拥塞均违约时生成保守关联假设，并建议进一步核对路径位置；全局拥塞不支持该解释时会保留反证。这个设计诚实且有用，但仍是规则化的证据提示，不是广泛验证过的根因定位算法。C13E05

“还差多少”与“还能优化多少”必须分开

目标差距 / 约束余量

面积上限 103、当前 100，余量是 3；时序目标尚未满足，可以计算与阈值的距离。这是测量与阈值的算术关系。

上界约束：margin = limit - measured
下界约束：margin = measured - limit

当前 _headroom() 正是这种阈值余量计算。C12

可实现优化潜力

“在不违反功能和面积要求的情况下，还能改善多少 timing”需要探索证据、模型及误差范围。不能从单个 margin 直接得出。

第一版可以诚实地说“潜力未知，下一步实验旨在降低不确定性”，不必输出虚假的百分比。

3. L2 参数搜索：为什么不是让模型随便改几个数字？

把一次物理实现记作 y = F(x; D, P, s)。x 是授权参数，D 是设计，P 是协议和工具环境，s 是种子，y 包含指标、合格性和失败。Runtime 求一次 F；优化器选择下一组 x。这是两种职责。

H_t = {(x_i, 实测结果_i, 合格性_i, 失败_i, 证据_i)}
x_(t+1) = 上游策略(H_t, 目标, 搜索域, 剩余预算)
新结果 = Runtime 执行并经受保护评价
H_(t+1) = H_t 加入新结果

用 BO 解释“探索”与“利用”（教学原理，不是新建本地算法）

昂贵黑盒优化通常不适合把所有参数组合跑完。代理模型根据历史样本估计某组参数的结果与不确定性；采集策略在“预计更好”与“值得进一步了解”之间权衡。以下 Expected Improvement 只是帮助理解的通用最小化例子，不是对 A2 当前每轮策略的完整复刻：

EI(x) = E[max(0, f_best - f(x)) | H_t]

这个式子的意思是：在已有数据条件下，尝试 x 的预期改善有多大。涉及多个目标、失败和硬约束时，还要遵守明确的目标与可行性定义；不能用一个临时加权分数替换受保护评价。

当前锁定 A2 的原生路径包含 inspection、建模、GPR 反馈、配置与候选选择；平台 adapter 调用它的原生 workflow，并保存检索、模型调用、候选与上下文。应讲上游如何做研究决策，而不是在平台再写一套廉价 BO。提供模型替换和参数域绑定时必须披露其与论文环境的差异。C11R04

当前实证最值得展示的是“不合格也进入反馈”

A2 单反馈验收中，真实候选执行状态为 succeeded，但反馈 feasible=false；然后原生策略产生下一组候选。三个结论要分开：程序运行完成、工程要求达标、优化优于比较对象。此次只支持有界反馈集成，不支持后两项普遍结论。E02

4. L3 有限动作：动作有限，策略仍然可以很复杂

将状态记为 s_t，可用动作集合记为 A(s_t)。一个动作不是只有名字，还包含对象、参数和前置条件。动作产生候选状态，再经检查形成新观测。算法难点在于对哪里、何时、以什么顺序和参数做动作，而非无限增加命令。

合格 checkpoint
  → 诊断 / 原生策略选择获准动作
  → Runtime 在候选工作区执行变换
  → 必需的功能、物理和 QoR 检查
  → 接受、拒绝或继续；保留父版本与失败产物

OpenROAD 的 repair_timing 和 repair_design 已有原生实现，平台不需要重写相应引擎。把它们作为 L3 能力时，还要定义状态装载、允许写集、分析前置条件、验证与回退，而不只是包一层字符串调用。R10

可复用研究候选：ResizerAgent 的作者项目围绕 post-CTS 设计，根据 timing/物理反馈和历史选择修复计划与相关操作，适合作为“有限动作也能做研究闭环”的例子。它的环境、入口、许可、工具版本与平台 smoke 尚需单独 intake；本报告不宣称你们已接入。R05

5. L4 源码演化：不是让模型在 OpenROAD 仓库随便改

冻结实验协议与基线工具
  → 从最终未满足目标形成机制假设
  → 选定允许修改的源码范围
  → 上游演化插件产生 patch
  → 路径 / 权限检查
  → 独立构建、测试与原生检查
  → Runtime 执行固定设计流程
  → 受保护评价，保留全部候选与失败
  → 根据证据保留 / 拒绝 / 修订假设

源码改变后，候选工具二进制当然会改变。公平性不是要求“二进制完全不变”，而是把允许变化的引擎实现作为实验处理，将其他评价条件固定。需要绑定基线 commit、patch 哈希、构建配方、候选二进制、固定设计和评价版本，避免链接到缓存旧二进制或修改裁判。

GoalEvolve 的 2026 年 8 月预印本研究如何由最终目标差距定位主要瓶颈，再结合阶段证据缩小到机制与源码区域，并记录局部收益在下游的保留或退化。它比“源码随机搜索”更贴近 proposal 后半段。论文效果不等于本平台效果；本轮没有完成其可执行代码、许可和原生入口准入。R06

为什么局部收益不够？例如某个阶段的 timing 变好，后续可能产生面积、功耗或布线代价。仅展示阶段最优日志，会把下游问题隐藏掉。源码候选是否有价值，必须回到事先冻结的完整评价条件；单次改善也不能证明跨设计泛化。

6. 外层如何决定先查询、继续 L2，还是申请 L3/L4？

建议架构，非已验证通用规划器分两步做：第一步由确定性控制逻辑筛掉不合法动作；第二步由获准的研究策略在合法集合中选择。不要让 LLM 自行决定自己是否有权限。

A_legal = 注册能力 ∩ 当前状态可用 ∩ 用户允许 ∩ 环境可用 ∩ 预算可承受
下一行动 = 策略(目标, 证据, 未知项, 历史, A_legal)
观察到的情况建议行动方向不能直接推断
缺关键路径或阶段数据先查询或补充分析；说明成本与想排除的假设。没有数据，所以修改所有相关参数。
有合法搜索域，预算获准调用 L2，保留其内部原生策略。所有用户的固定约束都与现有 A2 域相容。
适用 checkpoint + 已准入局部能力根据诊断证据考虑 L3；满足前置验证。一次不改善就说明必须修改引擎。
证据支持机制限制，且允许源码实验申请明确范围的 L4 独立实验。源码修改必然比参数搜索强。
预算用尽、目标已达成或风险过高停止、交付现有最优可行结果与未解决项。为了展示“反思”而继续跑。

停滞判断只是控制信号，不是算法最优证明

当前 convergence 分类会检查同协议的有效尾序列：最新失败或成功点不足则 unknown；方向归一化后，以绝对/相对容差判断改善、连续退化或窗口停滞。它不丢掉失败再拼出“好看的曲线”。stalled 不等于全局收敛，更不等于已证明需要 L4。C20E08

情况系统应做什么

10. 怎样证明工作台真的比固定脚本强？

建议评价协议围绕小而明确的任务集冻结支持范围与预算，对比相同工具集合下的固定流程、基础工具 agent 和增强策略。不要给增强策略更多预算、隐藏标签或额外工具，再把优势归因于“智能”。

  • 目标保持：不同表述是否保持同样的硬约束、未知项和授权范围。
  • 行动合法：是否正确拒绝缺 checkpoint、超预算、越权或不支持的操作。
  • 证据响应：反馈或反证变化时，动作是否发生合理变化；可以允许多个正确行动。
  • 诊断质量：是否命中任务允许的假设/检查范围，是否给出可定位证据，而非仅评价文笔。
  • 最终价值：成功率、可行结果、最终 QoR、达到目标所用预算、失败和恢复率；预测单列。
  • 可复现性：多设计、多种子与独立复跑；保留失败，不只报最好一个。
实际建设顺序：先让一个边界明确的任务做到“有证据地选择/拒绝行动”，再扩任务集和研究策略。不要把“准确预测所有设计的最佳工具”作为第一版上线条件。

2. 优先级最高的五个问题

P0 · A2 当前协议与固定用户目标存在语义差距

证据：评价代码以候选 CLK 作为对应时钟输入，元数据标注 candidate-variable-clock-signoff 和 fixed_sdc_fair_comparison=false；handoff 构建完整上游域及预算。C14C15

影响：不能把“面积至多增加 3%、不改 SDC、最多 3 次”的 L1 请求，无条件解释成同一目标下的 151 次 A2 可变时钟优化。代码有授权记录，并不自动证明所有用户约束已经作了等价映射。

建议：先明确分成两种实验语义：固定用户目标的工作台任务、完整上游研究协议的 A2 campaign；跨越时展示差异并重新授权。固定目标模式是否能由上游原生支持，须先验证；不得为了兼容而静默冻结搜索维度、改评价器或宣称精确复现。

P1 · Tutorial 的源码 hands-on 仍没有真实闭环验收

证据：当前治理总览只审 L1/L2；产品角色允许列表列出 RTLScout、A2、ORAssistant 与独立 3D，不能从中推出已完成 L3/L4 教程能力。C05

影响：如果今天把“已有插件架构”汇报为“proposal 已实现”，专业听众会追问 patch、构建和完整评价证据，而现有 L1/L2 smoke 无法回答。

建议：一个上游、一个机制、一份明确改动白名单、一个受保护设计和预算；先完成原生源码候选闭环，再谈平台接入。失败候选也能教学，但不能没有真实执行。

P1 · 诊断名称与算法能力需要分层说明

证据：_headroom() 是阈值余量；diagnose_runtime() 主要做事实归一化、保守假设和下一步检查建议。控制状态验收是 role/state replay；当前跨阶段实验恢复已知干净版本，而非自动生成新修复。C12C13E06E03

影响：“diagnosis-agent”“repair-agent”“PDAgent-style”这些名字容易让人误以为实现了上游完整算法。结构启发、数据接口、原生算法复用、准确率验证必须分别标注。

建议：界面分开显示事实、未知项、规则提示、模型假设、验证过的结论；补充任务集测试，而不是增加描述性组件。

P1 · 有多个能力入口，但还不是一条一致的用户旅程

证据：治理验收文档明确指出 SpecIR、RTLScout、诊断/恢复和 A2 还没有全部整合成一个完整用户界面。工作台服务与旧网页并存；旧页面仍包含“唯一 BO/GP 优化入口”文字，与当前 A2 产品口径冲突。该结论来自静态源码，未做浏览器操作验证。C16C24E10

建议：先做同一 Goal、候选谱系、Runtime 和协议的只读整合与导航，不在 UI 重算权威状态；之后再加最小提交动作。不要一次重构 API、UI、Runtime 和优化器。

5. 正式停止记录：固定目标与上游协议不等价

Problem：固定 SDC、严格小预算的用户任务，与当前完整 A2 可变时钟实验不是等价协议。

Evidence：fixed_sdc_fair_comparison=false；完整 12 维搜索域；151 次预算配置。C14C15E10

Why the current plan fails：若仅把“L2 插件已接入”视作所有 L1 目标的透明延续，会使用户约束和实验比较口径发生变化。

Option A：保留上游原生研究协议为独立明确授权的 campaign；固定用户目标任务保持原边界，缺优化能力时直接说明。

Option B：先核实上游是否原生支持所需固定目标；可支持则单独审查适配与验收，不可支持则寻找其他获准能力或与上游合作。

Recommendation：今天采用 A 的汇报口径，同时把 B 列为前置研究任务。不修改评价器，不悄悄裁剪维度，不把两类结果合成一条公平比较曲线。

6. 给你个人的建设建议

  • 不要一个人扮演所有算法作者。你要能解释输入、输出、状态、评价和研究边界；上游作者负责算法内核，这是平台路线的优势。
  • 每次只追一个闭环缺口。例如“同一 run 的失败证据能否驱动可审计恢复”，而不是一次要求“更智能、更漂亮、更通用”。
  • 用证据区分工程成果和科研贡献。原生接入、权限、恢复与公平协议是有价值的工程成果；通用规划、更优 QoR 或诊断算法是需要对照实验的研究主张。
  • 少报功能数，多报可复查任务。一个失败被正确识别、恢复并保留证据的案例，比十个没有验收的 agent 名字更有说服力。

3. 外部项目 intake：七项缺一不可

  1. 身份：canonical URL、维护者、精确 commit，不使用未固定分支头。

5. 原生研究逻辑与 adapter 到底怎么划线？

允许的薄适配需要停止评审的变化
把 approved observations 映射为上游读入格式。因为格式复杂，改成自己用几条规则选择参数。
把工作目录改成 attempt 私有目录，并保留所有输出。直接修改共享 ORFS 或删除旧结果，让上游脚本跑得通。
把上游 checkpoint、提案与原始轨迹转成明确产物。丢弃失败、只保留最好一次，或拿插件自报分数当 canonical QoR。
在准入时声明支持的输入范围与不兼容项。悄悄缩减搜索域、增加本地 fallback，再宣称完整复现上游。
把凭据调用替换为平台运营者批准的提供方式，并披露模型差异。把替换后的模型与硬件结果写成未经限定的论文复现。

6. 注册成功不等于成为产品默认能力

PluginRegistry 回答“安装了什么、哪个版本具备什么能力”；ProductSurface 回答“哪个身份可承担某个产品角色”。当前默认 RTL、L2 和知识角色分别对应 RTLScout、A2-ORFO、ORAssistant。新增 manifest 不会自动成为默认按钮，也不应靠注册顺序覆盖现有角色。C05

更改产品角色是维护者批准的独立产品决策，需有兼容性、证据和回滚记录。不要在普通插件 PR 中顺手更换默认优化器。

练习 3：判断公平比较

练习 4：判断源码贡献

源码 patch 让布局阶段更好，最终布线却更差。应该保留还是拒绝？

参考答案

按冻结的最终目标、约束和统计决定；阶段收益可以作为机制证据保留，但不能取代最终评价。若目标未改善且无其他获准价值，不应只挑局部指标宣布成功。

5. 老师可能追问的六个问题

你们自己的贡献是什么？是不是只是拼接？

平台的工程贡献是版本化契约、权限、可靠执行、统一证据与公平评价，让独立研究项目可以比较和协作。若要提出科研贡献，则须进一步定义并验证新的跨能力策略、诊断方法或评测协议；不能把接入数量本身当作算法创新。

为什么不用一个大模型直接调 shell？

因为那会把用户意图、权限和任意进程混在一起，难以证明边界、复现和评价公平。模型应提出有类型的行动，平台再决定能否执行；研究能力越强越需要稳定边界。

什么时候才算真正智能？

不是看思考文字，而是看在同工具和预算下，是否准确保持目标、处理未知、根据反证改变动作、避免无用执行，并获得更可靠的可行结果。必须用任务集和失败例评价。

现在可以给用户流片吗？

当前目标和证据属于教学/研究级实现，不足以承诺可直接流片。交付需说明功能检查、物理检查、时序/功耗分析和其他签核项目的覆盖及缺失；不把一个 GDS 文件当作所有签核通过。

为什么不马上补上 L3/L4？

要先有真实上游、许可、准确环境、最小入口和固定评价。否则很容易为了做出按钮，在平台内部重写弱算法或修改评价。今天先清楚说明缺口，随后逐项准入。

其他人怎么并行加入？

维护者先给已评审契约和集成基线，贡献者在独立分支写不同插件/模块；每项提供原生与平台 smoke，产品角色和共享执行由维护者统一批准。详见贡献者指南。
