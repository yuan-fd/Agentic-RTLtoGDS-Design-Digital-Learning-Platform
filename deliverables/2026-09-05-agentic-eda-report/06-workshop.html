2. 今天可以安全展示的三条证据回放

演示 A：自然语言规格到版图，不把小样例说成通用设计

  1. 展示原始中文规格：8 位无符号、无时钟组合加法、输出低 8 位。
  2. 展示 SpecIR、冻结验证要求和 65,536 输入检查；解释为何这是该小组合任务的穷举，而非任意状态系统的验证。
  3. 展示原生 RTLScout 的候选与检查链：lint → simulation → mutation → ORFS。
  4. 展示 GDS artifact 哈希、run/attempt 和通过的终态，不必现场再次耗时执行。
  5. 结束时明确：一个任务的集成证据，不是公司规格书通用支持。

来源：E01。本轮重新核对对应 RTL/GDS 等可定位产物哈希；原执行耗时是历史 receipt，不作为今天的运行计时。

演示 B：为什么“运行成功”仍要反馈失败？

  1. 显示上游 A2 的首次候选；说明搜索域与变量时钟协议。
  2. 显示 Runtime 的真实执行终态 succeeded。
  3. 显示受保护反馈里的 feasible=false，解释工程合格性与执行状态不同。
  4. 显示第二次原生策略产生的新候选及其 evidence/checkpoint。
  5. 说明该 smoke 使用历史 ORFS 观察初始化，不是从零完成整场实验；候选变化不单独证明因果理解或 QoR 改善。

来源：E02。完整 151 次预算只是配置证据，不要把它作为已有执行数量放到图表中。E10

演示 C：真实后端失败后如何继续？

  1. 说明故障是冻结的、平台自有的测试条件：功能检查可通过，但真实后端综合失败。
  2. 展示失败日志与没有编造 QoR 的诊断；当前记录中失败分类仍有 unknown，不能说系统已精确自动找到所有根因。
  3. 展示类型化 restore plan：指向此前验证过的直接祖先候选与精确 RTL SHA-256。
  4. 展示恢复后重新 compile/verify、simulation 与 ORFS 完成。
  5. 保留失败分支，强调不是删除失败或改写旧记录；也不是官方 CLOSER-Bench 成绩。

来源：E03。它适合讲可靠性和 provenance，不应被包装成一般化的自动 RTL repair 算法。

3. 三小时 Workshop 议程（目标方案，含尚未完成部分）

时间内容参与者动手 / 验收
0—20 分钟Agentic EDA、目标/状态/工具/反馈/验证；平台边界。从一句模糊目标中找出必须追问的约束。
20—45 分钟公共契约、Policy、Runtime、原生工具与产物。识别一个合法调用与一个越权调用，解释拒绝原因。
45—75 分钟Hands-on 1：自然语言 → 查询/阶段调用 → 反馈与行动。每组给出一条目标、一条真实查询、一次有证据的继续/停止决定。
75—85 分钟休息与环境恢复检查。确认 workspace 与预算不混用，不重启共享 worker。
85—110 分钟黑盒优化、A2 原生策略、协议差异；L3 动作与 L4 机制。读懂一次不可行反馈；区分参数、设计变换和源码变化。
110—155 分钟Hands-on 2：受限源码候选 → 编译 → 固定流程评价。待建设：至少一个真实原生候选，有 patch、二进制、测试和评价。未具备时不能宣布此环节已完成。
155—175 分钟目标驱动演化、局部收益的下游保留、失败和公平比较。判断某个阶段改善是否真的使最终设计更好。
175—180 分钟总结与贡献方式。每组带走协议、证据清单与一个可执行的后续问题。

编译和完整后端可能超出课堂时长，应提前准备锁定环境与真实回放，现场运行获准的有界部分，并清楚标记“现场执行”和“预先执行回放”。不能为了缩短课堂时间，把不同评价流程的结果拼成同一比较。

4. 四个能让专业听众学到东西的练习

练习 1：判断状态

进程 exit 0，必需 GDS 缺失；另一次产物完整但 timing 未达标。两次分别算什么？

参考答案

第一次不满足执行/产物契约，Runtime 不得接受成功。第二次可以是流程成功、工程验收不合格。不要把二者压成一个“成功”布尔值。

练习 2：判断诊断

WNS 变差，同时全局拥塞增加。能否直接定位为拥塞根因？

参考答案

只能提出相关假设。需要路径位置、局部数据或受控干预；多参数候选的改善不能独立确定因果机制。

练习 3：判断公平比较

候选放宽时钟后违例减少，能否说在原用户目标下性能改善？

参考答案

不能仅凭违例减少得出。应检查评价语义与固定目标；当前可变时钟 A2 协议必须单独标注，不与固定 SDC 实验混比。

练习 4：判断源码贡献

源码 patch 让布局阶段更好，最终布线却更差。应该保留还是拒绝？

参考答案

按冻结的最终目标、约束和统计决定；阶段收益可以作为机制证据保留，但不能取代最终评价。若目标未改善且无其他获准价值，不应只挑局部指标宣布成功。

5. 老师可能追问的六个问题

你们自己的贡献是什么？是不是只是拼接？

平台的工程贡献是版本化契约、权限、可靠执行、统一证据与公平评价，让独立研究项目可以比较和协作。若要提出科研贡献，则须进一步定义并验证新的跨能力策略、诊断方法或评测协议；不能把接入数量本身当作算法创新。

为什么不用一个大模型直接调 shell？

因为那会把用户意图、权限和任意进程混在一起，难以证明边界、复现和评价公平。模型应提出有类型的行动，平台再决定能否执行；研究能力越强越需要稳定边界。

什么时候才算真正智能？

不是看思考文字，而是看在同工具和预算下，是否准确保持目标、处理未知、根据反证改变动作、避免无用执行，并获得更可靠的可行结果。必须用任务集和失败例评价。

现在可以给用户流片吗？

当前目标和证据属于教学/研究级实现，不足以承诺可直接流片。交付需说明功能检查、物理检查、时序/功耗分析和其他签核项目的覆盖及缺失；不把一个 GDS 文件当作所有签核通过。

为什么不马上补上 L3/L4？

要先有真实上游、许可、准确环境、最小入口和固定评价。否则很容易为了做出按钮，在平台内部重写弱算法或修改评价。今天先清楚说明缺口，随后逐项准入。

其他人怎么并行加入？

维护者先给已评审契约和集成基线，贡献者在独立分支写不同插件/模块；每项提供原生与平台 smoke，产品角色和共享执行由维护者统一批准。详见贡献者指南。

6. 今天不要说的五句话

  • “我们已经完成了完整 tutorial。”——源码 hands-on 尚未验收。
  • “我们的诊断准确率 100%。”——PostEDA 的 1.0 是单题派生集成诊断分。
  • “我们已经跑了 151 次 A2。”——目前这是配置预算，不是完成数量。
  • “我们的恢复等于自主修复任意 RTL。”——当前是一个受控已知 checkpoint 的恢复。
  • “接口齐全就说明 agent 可以解决任何用户问题。”——合法工具组合仍受能力和证据范围限制。
结束语：今天我们可以交付一个有真实证据的 L1/L2 基础，并清楚解释为什么还不是通用自主 EDA。下一步的重点是把同一目标下的决策与证据连起来，以及完成受保护的源码演化闭环，而不是继续增加未经验证的功能名。
编制基线：用户 proposal + 当前工作树 + 原始运行证据。结论、研究主张、设计建议分别标注。
