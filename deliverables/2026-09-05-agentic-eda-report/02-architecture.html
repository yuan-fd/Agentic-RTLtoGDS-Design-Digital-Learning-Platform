AGENTIC EDA / 平台架构与工作流

让专业插件协作，而不是重造算法

从用户确认 spec 的下一秒开始，逐步解释功能模块、代码职责、状态和执行链路。

18 MIN · 2026-09-05 · 文档审计，不是新增平台功能
完整单文件 / 适合发送老师
核心修正：L2/L3/L4 是“优化服务”，不是设计从无到有的全部步骤。平台还需要需求契约、前端设计、功能验证、基础实现、证据接口和交付服务。这些服务可以调用插件，不必由平台重写算法。

2. 从一个 UART 改造规格开始：第一次工作不是优化

教学设计示例，未验收用户希望在经典 UART 上增加 APB 接口、深度 16 的接收 FIFO、可配置波特率和错误状态，使用指定开源工艺完成教学级版图。这个示例用于解释职责，不能拿当前 8 位加法器验收替它背书。

① 需求澄清：先把“对”定义出来

输入：规格书、自然语言、可复用项目版本。工作：澄清 FIFO 满/空行为、复位、寄存器语义、配置生效时机、接口时序、时钟和验收目标。输出：用户确认的 SpecIR、需求编号、验证计划、DesignGoal、权限和预算。

系统不能把“低功耗”偷偷解释为任意数值。默认值要标成建议，经确认后再冻结。对于上传文件，本次未验证已具备通用 PDF/DOCX 规格摄取能力。

② 执行前检查：决定任务是否具备条件

检查可复用源码权限、接口和工艺支持、验证入口、工具环境、输入哈希、资源预算。输出可执行计划或具体阻塞项。此时不需要 L2，也不应该盲目生成 RTL。

③ 前端设计插件：产生第一个候选

调用获准 RTL 生成/复用能力，保存候选与来源。验证组件依据冻结需求检查候选，把编译、仿真、反例等反馈给原生设计插件。这里已经有“候选 → 检查 → 修订”的闭环。当前原生 RTLScout 的单任务例子有真实证据。E01C26

④ 前端验收：形成精确 checkpoint

区分语法可编译、功能通过当前检查、测试质量三个结论。同一模型生成 RTL 和 testbench 互相认可，并不足以证明需求正确。保存需求版本、冻结 oracle、验证覆盖、候选哈希与未覆盖项。

当前加法器的穷举对这个组合逻辑任务很有说服力，但不能外推到包含复杂状态的设计。mutation gate 说明测试能捕获所选扰动，也不等于任意缺陷都可检测。

⑤ 基础实现：建立第一份物理证据

Runtime 提交受控综合/布局/CTS/布线任务，采集阶段报告与最终结果。baseline 是比较基准，也是把“这个设计在此条件下怎么样”变成事实的第一步；它不是 L1 的全部价值。

⑥ 观察与优化：此时才挑选 L2/L3/L4

目标已满足则交付；信息不足则补充查询；适合参数搜索则请求 L2；具备受控 checkpoint 和局部修复能力才考虑 L3；证据和授权支持机制实验才考虑 L4。没有适用能力时必须停止或请求人工，而不是让模型自行执行 shell。

⑦ 交付：给结果，也给剩余风险

交付规格版本、RTL、验证结果、GDS、约束、工具版本、QoR、失败历史和未满足项。应明确“教学级”，不以文件存在代替功能或签核结论。

3. 三种工具粒度：命令、平台能力、优化 campaign

层级例子谁承担责任
OpenROAD 原生命令repair_timing、repair_design 等原生功能。R10OpenROAD 实现优化机制；必须满足它的设计状态与分析前置条件。
平台语义工具query_timing、run_stage、compare_runs。C04Policy 验参数、Runtime 执行与登记、适配器映射。一个平台工具可能封装多条审查过的原生命令。
研究能力 / campaign在冻结搜索域和预算下运行 A2 参数搜索。C10上游拥有候选生成；外层控制器持久化阶段与预算；不能由 HTTP handler 长时间运行 EDA。

同一个命令可以出现在不同层级的任务里。固定流程调用一次修复，与围绕 checkpoint 自适应编排修复动作不同；修改该命令的实现则是源码级优化。不要用命令名字代替修改权限的定义。

5. 一次请求在代码里怎样旅行？

用户 / API
  → SpecIR 或 GoalDraft → 用户确认的 DesignGoal
  → SemanticToolCall（类型化操作，不是 shell）
  → Policy（目标、当前状态、能力、权限、预算）
  → TaskSpec（冻结输入与参数、超时、产物要求）
  → WorkflowRuntime（run → stage → attempt）
  → ProcessAdapter（私有工作区与有界进程）
  → 上游原生工具 / 插件
  ← PluginResult + 原始日志 / 候选 / checkpoint
  → 退出码、路径、类型、哈希等校验
  → 受保护评价：实测指标与合格性
  ← 持久化事件、ToolReceipt、下一次观察

公开契约分别定义 TaskSpec、PluginManifest 和 PluginResult。插件返回 succeeded 只是待验证的结果声明；Runtime 还要核对进程退出和必需产物。优化目标是否满足，又是另一层判断。C01C02C03C06

6. A2 的两层循环：不要让工作台抢算法的工作

外层：用户目标 / 授权 / 能力选择 / 停止与恢复
   └─ A2 campaign 的持久化控制器
       ├─ 调用原生初始化或策略插件 → 参数候选
       ├─ Runtime 调 ORFS 候选执行器
       ├─ 受保护评价 → observation
       └─ observation 回到原生 A2，生成下一轮候选

A2 adapter 调用锁定源码中的 OptimizationWorkflow 与 run_iteration()；当前还在提案生成前绑定同一上游 commit 的完整参数约束，因为原生硬编码范围与发布的约束文件存在差异。这是需要披露的适配，不应说“零改动精确论文复现”。平台没有在返回候选后偷偷裁剪维度。C11E02

恢复 controller 应重新加载已存在的 run ID 与 checkpoint，不能因为浏览器刷新就再花一次 EDA 预算。HTTP 负责调度和返回 ID，独立 worker 负责获准执行。C10C23E10E16

7. 冻结什么，允许变什么？

实验可变对象必须单独保护的对象
前端设计迭代候选 RTL；每版有独立哈希和谱系。已确认 spec、独立验收条件、oracle。不能改测试答案使候选过关。
固定目标的 L2事先授权的参数域。RTL、PDK、验收 SDC、目标、评价规则、种子策略和比较预算。
当前 A2 上游协议完整 12 维域，包括候选时钟。固定的是“搜索/评价协议”，不能把它混成固定 SDC 实验。C14
L3 局部动作授权 checkpoint 上的指定设计变换。功能、外部约束与受保护评价；每个候选必须保存可回退来源。
L4 源码演化独立源码工作区的获准引擎文件与候选二进制。基线版本、编译配方、设计/PDK/SDC、测试、评价和统计。候选工具变化是实验处理，不是允许评价器变化。
协议变化必须显式：当前源码显示 L2 请求会申请完整 151 次预算并进入可变时钟域。演示时必须把它讲成单独授权的研究 campaign，而不是原封不动地继续“最多 3 次、不改 SDC”的任务。后续若要支持用户固定目标，须先解决协议映射并通过治理，不可今天直接改受保护评价器。C15C14
编制基线：用户 proposal + 当前工作树 + 原始运行证据。结论、研究主张、设计建议分别标注。
